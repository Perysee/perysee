# 004. Tracker installation check

Status: proposed

## Context

When nothing shows up for a site, the cause is almost always outside the application: a script that is not loaded, a domain that is not allowed, a consent setting that differs between the snippet and the site, a cached page, a firewall in front of the collector. The collector knew, but only kept one global counter of refusals (`collection_rejections`), without a site, a cause or a host, and the tracker is silent by design, so the person installing it had no way to find out.

The collection path is the most sensitive code of the product (COL-01: an event is acknowledged with 204 only once it is stored) and an idle instance has a hard query budget (30 queries on SQLite, 40 on MariaDB for one pass of every scheduled command, pinned by `IdleSchedulerCostTest`).

## Decision

- **Typed refusals, same answers.** Every refusal of the collector is a `CollectionRejected` exception carrying a `RejectionCause` (`unknown_site`, `domain_not_allowed`, `consent_missing`, `quota`, `invalid_payload`, `mode_mismatch`, `path_excluded`). It extends `HttpException` with the status the plain `abort()` used, so the codes and the bodies are unchanged (frozen by `CollectionRejectionCharacterizationTest`). The shape checks and the validation now run inside the same `try`, so the 413, 415 and 422 refusals of the request itself are counted too; this changes the figure shown as "Collection rejections" on the instance health page, which now includes them.
- **Written after the rollback.** A refusal is filed in the `catch`, outside the transaction (a write inside it would be rolled back with the rest). The accepted path does not change: a read of the site and an insert, plus one update on the very first event of a site. A test pins that statement list, so any added query fails the build.
- **One aggregated row, not one row per request.** `collection_diagnostics` has the primary key (`website_id`, `bucket_start` hour, `cause`) and a `hits` counter incremented by an upsert. Its columns hold no address, user agent, path or payload. `sample_host` is the host of the `Origin` header, and only for `domain_not_allowed` and `unknown_site`, after being checked as a plain host name. `website_id` 0 means "the instance": a request that could not be tied to a site. A forged site key is never stored.
- **Bounded cost under attack.** Writes are limited to 20 a minute for each site and cause (`Coordination::throttle`, so a module that moves the throttle elsewhere moves this too), shared by every visitor and not keyed by address. Beyond that only the cache counter that already existed moves, which makes the displayed counts a floor ("at least N"). Resolving a site from a key that appears in an unattributed request costs one indexed read, behind the same limit. The limit is global for the unattributed rows, so a flood of invalid payloads can hide a legitimate site's invalid payloads: accepted, because the page also reports the other causes.
- **"Test now" without an event.** The browser of an owner asks `POST /sites/{site}/tracking/probe` (6 a minute) for a token: an HMAC, keyed by `APP_KEY`, of the public site id and an expiry within ten minutes. It then posts a normal payload to the real `/api/collect` with the header `X-Perysee-Probe`. After validation, the collector recognises a valid token for that site and answers 204 with the header echoed, after reading the site and upserting a `probe_ok` row. It writes nothing to `events` and does not touch `first_collected_at`, so the reporting timezone stays unlocked and the statistics cannot include it, without a filter to maintain. A failed write is a 503 like any collection failure; probes are limited to 12 a minute per site and do not use the visitor quota. A missing, expired, forged or foreign token follows the normal path. The header is a custom one, so an `OPTIONS /api/collect` route answers the preflight, which the administration needs when it is served from another origin than the script.
- **What the test cannot prove.** It comes from the administration, not from the tracked site: it proves the address, the firewall, the site key, the mode and the database, but not the allowed domains, the consent banner or the page cache. The page says so, and only a real event proves the whole chain.
- **Reading.** `TrackerCheck` reads the newest event (`idx_site_recent`), the volume of the last 24 hours (counted up to 10,001 rows, shown as "10,000+") and the aggregated rows. Nothing is added to `events` or `websites` per event. The page is an Inertia screen with a lazy `check` prop so that "Refresh" reloads only that. Owners and viewers read; only owners test. An administrator who is not a member has no access.
- **Quiet sites.** `SiteActivity` adds `last_event_at` and `silent` to the sites of a list (one grouped query for at most one page). A site is silent when it received events but none for `perysee.silent_site_days` (3 by default, `PERYSEE_SILENT_SITE_DAYS`), or when its raw events were all removed by retention after it had been measured.
- **Retention.** Seven days. A dedicated command, `perysee:prune-diagnostics`, runs hourly with `withoutOverlapping`, in batches. The maintenance command that the idle budget measures is not changed, except that deleting a site now also removes its rows.
- **Migration.** `2026_11_08_100000_create_collection_diagnostics_table` is additive and guarded by `Schema::hasTable`.

## Consequences

- The count of refusals on the health page rises for instances that receive malformed requests, because the shape refusals are now counted.
- A tracked site that is blocked by CORS, an ad blocker or a cookie refusal never reaches the collector: those causes are only deduced by elimination (nothing received, nothing refused) and the advice says so.
- The refused responses carry no CORS header, so a browser console on the tracked site shows a CORS error instead of the 403. That is unchanged and documented.
- The counts are floors by design. The seven day window and the per-hour buckets mean a long outage is shown as a series of hours, not a precise number.
- F3 (event values) will also modify `TrackingController`. The additions of this change are three localised blocks: the typed refusals, the enlarged `catch`, and the probe branch right after validation.

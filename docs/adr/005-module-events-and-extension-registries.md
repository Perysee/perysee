# 005. Module events and extension registries

Status: proposed

## Context

Modules could add screens, navigation, branding and health cards, but not react to what the Core does: an alerting or digest module had nothing to subscribe to, no way to notify someone, and no source of figures for a report. Hosting is shared and has no worker (ADR 003), the collector is the one path that must stay fast and quiet, and a module is third-party code that can fail, so any hook has to be cheap when unused and isolated when used.

## Decision

- **A dedicated bus, not the Laravel dispatcher.** `App\Modules\Events\DomainEvents` carries a stable catalog of eight events (`goal.converted`, `aggregation.completed`, `scheduler.heartbeat_missed`, `ingest.backlog_exceeded`, `team.invitation_accepted`, `share.created`, `share.revoked`, `module.quarantined`). The framework dispatcher would expose every Eloquent and framework event, an unstable surface, and would propagate listener exceptions to the publisher. Modules subscribe with `ModuleProvider::listen(EventClass::class, $closureOrInvokableClass)`.
- **Payloads are anonymous.** Each event is a `readonly` class with scalars and lists of scalars: identifiers, counters, enumerations and ISO 8601 UTC dates. Never an address, a name, an IP, a token or token hint, a free label, an exception message or a path. A contract test snapshots names, fields and types, and fails on a removed or retyped field. Fields are only added; removing or changing one needs a new schema version and a release note.
- **The module API stays at version 1.** The additions are backward compatible. A module that uses them states the first Core release that has them (`ModuleApi::DOMAIN_EVENTS_SINCE`) in the `core` field of `module.json`; an older Core already refuses to enable a module that needs a newer one. `ModuleProvider::listen`, `notificationChannel` and `reportSource` also throw a clear error if the manifest asks for an older Core, so a manifest cannot claim support it does not have. A future incompatible change is the only reason for API 2.
- **Synchronous, best effort, never in collection.** Delivery is in-process, at most once, without ordering between modules, and without replay. Scheduler paths publish after the batch is committed and the aggregation lock is released, never inside a transaction (which can be replayed). Administrator requests publish after the response (`terminating`). The collector and `app/Analytics/Ingestion` never reference the bus; a test enforces it and compares collector queries with and without a listener.
- **Zero cost when nobody listens.** Listeners live in memory for the request, so there is nothing to store. Publishers ask `listening()` first and compute or read nothing otherwise. With a listener the extra cost is at most one read on an idle scheduler pass (the previous heartbeat).
- **Isolation.** Every listener runs in its own `try/catch (Throwable)`. A failure is counted by `ModuleFailures` against the module that registered it, which also provides the quarantine. Between listeners the module is re-checked: one that was disabled or quarantined meanwhile receives nothing. An event about a site reaches only modules active on that site. One delivery has a time budget (`perysee.module_events.budget_ms`, 2000): the listener that uses it up counts as failing and the remaining listeners are skipped. An event published during a delivery waits for it, and a chain is capped, so a quarantine announced by a failing listener cannot loop. PHP cannot interrupt a listener in progress: an infinite loop or a fatal error is not caught. A module is trusted code; the recovery is `PERYSEE_MODULES=false`.
- **No migration and no queue.** The "once per incident" markers (`domain_events:heartbeat`, `domain_events:backlog`) are rows of `analytics_state`, claimed with an atomic `INSERT OR IGNORE`, released on recovery. There is no outbox.
- **Heartbeat honesty.** A stopped scheduler cannot report itself. The event is published from an administrator's page while the scheduler is silent (`recovered = false`) and when it runs again (`recovered = true`). Without an administrator or a recovery there is no event. Monitoring from outside remains necessary.
- **Registries.** `NotificationChannels` and `ReportSources` are singletons like `ModuleExtensions`. Keys are `<module id>.<name>` (the Core's are `core.…`), unique, and a module cannot register another's prefix. `NotificationChannels::send()` never throws, removes secrets from messages with `InstanceMailer::scrub` before logging and counts failures against the owner. `Notification` and `ReportSection` are plain text with capped lengths and counts. The Core provides the channel `core.mail` (through `InstanceMailer`, so it follows the instance SMTP settings) and the report source `core.traffic` (pageviews, sessions, custom events and goal conversions from the consolidated statistics).

## Consequences

- Alerting and digest modules, and the Slack, Telegram and webhook channels, can be built outside the Core. None of them is part of this change.
- Delivery can be lost (crash between commit and publication, a listener that fails) and is never repeated. Modules must treat events as hints and read the data when they need certainty.
- A slow listener delays the scheduler pass that published (cron) or the end of the request of the administrator who triggered the action (HTTP, after the response under FPM), never a visitor's request.
- `member_id` in `team.invitation_accepted` is an internal identifier. It is the only user-related field; removing it later would need a new schema.
- Quarantine counts failures within a ten-minute window, so rare events such as the heartbeat cannot reach the threshold alone; the failures are still counted and logged.
- The minimal Core version for events is a constant (`ModuleApi::DOMAIN_EVENTS_SINCE`, currently `0.4.0`) that must match the first release shipping this change.
